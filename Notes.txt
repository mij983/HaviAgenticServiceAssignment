Overview
This project is an AI-powered ticket routing system that predicts the correct assignment group/team for IT support tickets.

It uses:

Semantic Search (vector embeddings)

Knowledge Base documents

Historical ticket data

Local LLMs via Ollama

ChromaDB vector database

The goal is:

User enters a new incident/ticket → System predicts the best assignment group automatically.

Hi Team, today I’ll walk through the Havi Agentic Service Assignment project.
This project is an AI-powered intelligent ticket routing system designed to automatically predict the correct assignment group for IT incidents.

The main goal of the project is:
When a user creates a ticket, the system should intelligently identify which support team or assignment group should handle that issue.

Overall Architecture
The complete flow works like this:

User submits a ticket
→ The ticket goes through preprocessing
→ Text embeddings are generated
→ ChromaDB performs semantic similarity search
→ Similar historical tickets and KB articles are retrieved
→ The LLM analyzes the context
→ The system predicts the best assignment group
→ Confidence and explanation are generated

So overall, this is a Retrieval-Augmented Generation or RAG-based AI architecture.

Step-by-Step Workflow
Step 1 – User Ticket Input
The user enters a ticket description.

Example:
“Unable to connect to VPN after password reset.”

The request comes into the web application backend and is passed to the prediction pipeline.

Step 2 – Preprocessing Agent
The preprocessing agent cleans and normalizes the ticket text.

Activities include:

Removing special characters

Removing ticket IDs

Converting text to lowercase

Cleaning unnecessary spaces

Normalizing the sentence

Example:

Before:
“INC000123 – VPN ISSUE!!!”

After:
“vpn issue”

This step is important because cleaner text improves embedding quality and search accuracy.

Step 3 – Embedding Generation
After preprocessing, the embedding agent converts the text into vector embeddings.

We use Sentence Transformers models such as:

all-mpnet-base-v2

all-MiniLM-L6-v2

These models convert human language into mathematical vector representations.

Example:
“vpn access issue”
becomes:
[0.234, -0.781, 0.991, ...]

The benefit of embeddings is semantic understanding.

For example:

“VPN not working”

“Unable to connect VPN”

“Remote access failure”

All these become semantically similar even though keywords differ.

Why We Use all-mpnet-base-v2
We selected all-mpnet-base-v2 because:

It provides excellent semantic similarity accuracy

Better contextual understanding

Strong sentence embedding performance

Good balance between speed and quality

This improves ticket similarity matching significantly.

Step 4 – ChromaDB Semantic Search
The generated embeddings are searched against embeddings stored in ChromaDB.

ChromaDB acts as the vector database for the system.

Stored data includes:

Historical incidents

KB articles

SOP documents

Troubleshooting guides

The search works using cosine similarity.

The system retrieves the most similar historical tickets.

Example:

VPN login failure → Network Team
VPN authentication issue → IAM Team
Remote access problem → Network Team

This gives contextual knowledge to the AI.

Historical Ticket Training Process
The historical training flow is:

CSV historical tickets
→ Preprocessing
→ Embedding generation
→ Store embeddings in ChromaDB

Each ticket embedding is stored along with:

Assignment group

Resolution information

Metadata

Ticket description

This creates a searchable organizational memory.

Knowledge Base Training Flow
Apart from incidents, we also ingest KB documents.

Supported formats:

PDF

TXT

Markdown

HTML

The document ingestion flow is:

Documents
→ Text extraction
→ Chunking
→ Embedding generation
→ Store in ChromaDB

Chunking is important because large documents are split into smaller AI-searchable pieces.

This helps retrieval quality and reduces token overload.

Step 5 – LLM Reasoning Layer
After retrieval, the LLM agent receives:

Current ticket

Similar incidents

KB documents

Candidate assignment groups

The LLM then performs reasoning.

We use local LLMs through Ollama such as:

Gemma

Mistral

Llama

The LLM analyzes all retrieved context and predicts the best assignment group.

Example reasoning:
“Similar VPN incidents were historically assigned to Network Support.”

Why We Use Local LLMs
Benefits include:

No external API dependency

Better data privacy

Lower operational cost

Offline capability

Faster internal processing

This is important for enterprise IT environments.
